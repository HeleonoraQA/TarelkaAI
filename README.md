# Tarelka

**Планировщик домашнего питания.** Недельный план, рецепты и список покупок — в одном приложении. Прототип работает локально; серверная часть на Supabase (Auth, Postgres, RLS) подготовлена, а контракт подключения фронта согласован и описан в [Серверная часть](#серверная-часть-supabase-auth-rls-и-политики). До реализации код по-прежнему использует `localStorage` и `js/data.js`.

«Раз в неделю собрать план, один раз сходить в магазин и готовить без лишних решений.»

## Что это

Tarelka — веб-приложение (PWA) для планирования домашнего питания. Пользователь проходит короткий онбординг (категория питания, аллергии, количество человек), получает **готовый план на неделю** и **автоматически собранный список покупок** по отделам магазина.

**Для кого:** занятые люди 25–45 лет, готовят дома 3–5 раз в неделю, хотят есть разнообразно и не тратить час на планирование.

**Главный сценарий:**

Онбординг (3 шага) → План недели → Рецепт → Список покупок

**Принципы:**

1. План важнее каталога — главный экран это неделя, а не лента рецептов.
2. Готовый результат с первого запуска — онбординг заканчивается планом, а не пустым экраном.
3. Только тапы — никаких свайпов, долгих нажатий и drag-and-drop.
4. План и список — одно целое: изменение плана сразу отражается в покупках.
5. Приватность по умолчанию — аналитики нет; пользовательские данные привязаны к личному `user_id` и защищены RLS. Без сети доступно только чтение кэша.

## Что сделано

1. **Схема данных из PRD — сущности, связи** в `docs/architecture.md` §8.1, §9.1: `profiles`, `week_plans`, `checked_items`, `manual_items`, `imports`, нормализованный каталог рецептов.
2. **БД и подключение агента** — hosted Supabase подключён через MCP; миграции и сиды лежат в `supabase/migrations/20261124140000_catalog_schema.sql` и `supabase/migrations/20261124140100_catalog_seed.sql`, порядок описан в `README.md`.
3. **Auth** — вход/сессия через Supabase Auth REST, отдельный ключ `tarelka:auth`, файлы `js/config.js` и `js/api.js`; контракт в `docs/architecture.md` §11.2 и `docs/spec.md` §12.1.
4. **RLS** — политики `user_id = auth.uid()`; negative-тесты в `supabase/tests/rls_negative_tests.sql`, описание в `docs/architecture.md` §8.2.
5. **API по спеке через TDD** — CRUD плана/покупок и бизнес-сценарий сборки списка покупок реализованы RPC в `supabase/migrations/20261124152000_api_rpc.sql`; тесты в `supabase/tests/api_plan_tests.sql` и `supabase/tests/api_shopping_tests.sql`; контракт — `docs/api-openapi.yaml`.
6. **Фронт подключён к API** — живые данные: каталог, профиль, план и покупки; ошибки, offline read-only и одноразовый импорт `localStorage` в `js/app.js` и `js/api.js`; поведение описано в `docs/architecture.md` §11 и `docs/spec.md` §12.
7. **CORS и проверка в браузере** — preflight и запросы с `http://127.0.0.1:8080` проходят, каталог возвращает 18 рецептов; проверка зафиксирована в `docs/architecture.md` §11.7 и `docs/prd-prototype.md` §8.5.
8. **Скрин работающего бизнес-сценария сборки списка покупок** и **скрин результата прогона negative-тестов** в папке `/screenshots`.

## Возможности MVP

### Онбординг

- 3 шага: категория питания → аллергии → количество человек (2/4/6).
- Категории: «Без ограничений», «Много белка», «Лёгкое», «Щадящее». «Без ограничений» показывает весь каталог.
- Любой шаг можно пропустить, значения по умолчанию: «без ограничений», без аллергий, 4 человека.
- Настройки меняются позже в «Ещё → Мои предпочтения».

### План недели

- 7 дней (пн–вс) × 3 приёма пищи (завтрак / обед / ужин).
- Сегодняшний день выделен и `aria-current="date"`.
- Назначение рецепта в пустую ячейку через Discover.
- Удаление блюда с возвратом фокуса.
- «Собрать заново» — автоподбор по категории питания и аллергиям с минимумом повторов.

### Discover (выбор рецепта)

- Полноэкранный диалог; открывается из пустой ячейки плана, день уже выбран.
- Поиск по названию и ингредиентам.
- Фильтры-чипы: «До 20 минут», «Завтрак», «Обед», «Ужин».
- Жёсткие ограничения (категория питания + аллергии) применяются всегда.

### Карточка рецепта

- Крупная иллюстрация, название, вступление, время, порции, теги.
- Пересчёт порций 2 / 4 / 6: штучные округляются вверх, граммы и мл — до 5.
- «Добавить в список» — добавляет ингредиенты в покупки.
- «Добавить в план» / «Добавить сюда» (если пришли из ячейки).
- Дисклеймер по аллергенам.

### Список покупок

- Собирается автоматически из плана: агрегация по `name + unit + dept`.
- Группировка по 7 отделам в фиксированном порядке.
- Отметка купленного одним тапом + прогресс «X из Y».
- Ручное добавление позиций.
- Отметки сохраняются при изменении плана.

### Ещё

- «Мои предпочтения»: категория питания, аллергии, порции 2/4/6; сохранение сразу влияет на следующий автоподбор.
- «Данные»: «Сбросить всё» с подтверждением, после сброса — онбординг.
- «О продукте»: дисклеймер по аллергенам, локальное хранение, версия 1.0.

## Технологии и ограничения

| Слой | Что используем | Что **не** используем |
|---|---|---|
| HTML | Семантический HTML5 | — |
| CSS | Чистый CSS + CSS-переменные (`styles/tokens.css`) | Tailwind, Bootstrap, препроцессоры |
| JS | Vanilla JS (ES5-совместимый IIFE) | React, Vue, Svelte, jQuery, lodash |
| Сборка | Нет | npm, bundlers, транспайлеры |
| Шрифты | Системный стек + Inter, если установлен | Google Fonts, CDN |
| Иконки | Инлайн SVG-спрайт (Lucide-style) | Библиотеки иконок, внешние запросы |
| Хранение | `localStorage`: `tarelka:state` (кэш) и `tarelka:auth` (сессия); Postgres — источник истины после подключения | IndexedDB, service_role в клиенте |
| Изображения | Локальные SVG — финальный формат MVP (`assets/recipes/`) | Внешние URL, WebP, растровые фото |

**Жёсткие правила** (см. `AGENTS.md`):

- Все цвета, отступы, радиусы — только через токены в `styles/tokens.css`.
- Хардкод цветов в `main.css` и `app.js` запрещён.
- Аналитики и трекинга нет. До подключения API внешних запросов нет; после подключения единственный внешний адрес — Supabase из `js/config.js`.
- В текущем прототипе данные пользователя не покидают устройство; после подключения пользовательские данные хранятся на сервере, а офлайн доступен только кэш для чтения.

## Быстрый старт

Приложение статическое — сборка не нужна. Достаточно любого HTTP-сервера.

### Вариант 1: Python

```bash
python3 -m http.server 8000
```

На Windows обычно:

```bash
python -m http.server 8000
```

Открыть <http://localhost:8000>.

### Вариант 2: Node.js (npx)

```bash
npx serve .
```

### Вариант 3: VS Code Live Server

Открыть `index.html` через расширение Live Server.

> Не открывайте `index.html` напрямую через `file://`: service worker по такому протоколу не работает, а `localStorage` может быть недоступен.

### Развёртывание

Подходит любой статический хостинг: GitHub Pages, Netlify, Vercel, Cloudflare Pages.

Пример для GitHub Pages:

1. Запушьте репозиторий на GitHub.
2. Settings → Pages → Source: Deploy from a branch → `main` / `/ (root)`.
3. Откройте `https://<user>.github.io/<repo>/`.

После первого визита приложение кэшируется и работает офлайн.

## Как устроено

### Экраны

SPA-роутинг через `data-screen` на `<body>` и `section.screen[data-screen]`:

| `data-screen` | Экран | Файл / функция |
|---|---|---|
| `onboarding` | Онбординг (3 шага) | `#onboarding`, `showStep()` |
| `home` | План недели | `#home`, `renderPlan()` |
| `recipe` | Карточка рецепта | `#recipe`, `renderRecipe()` |
| `shopping` | Список покупок | `#shopping`, `renderShopping()` |
| `discover` | Выбор рецепта | `#discover`, `openDiscover()` |
| `more` | «Ещё» — хаб | `#more`, `renderSettings()` |
| `prefs` | Мои предпочтения | `#prefs`, `savePrefs()` |
| `data` | Данные и сброс | `#data`, `resetAllData()` |
| `about` | О продукте | `#about` |

Переходы — через `showScreen(name)` с сохранением стека навигации. Discover — полноэкранный диалог: `role="dialog"`, фокус-трап, закрытие по `Esc` и кнопке.

### Хранилище

Сейчас один ключ localStorage: `tarelka:state`. После подключения Supabase он останется офлайн-кэшем, а рядом появится отдельный `tarelka:auth` для сессии; источник истины станет сервер.

Схема `tarelka:state` (version 1):

```json
{
  "version": 1,
  "profile": {
    "onboarded": true,
    "diet": "none",
    "allergies": ["gluten"],
    "people": 4
  },
  "plan": [
    { "breakfast": "oatmeal", "lunch": "soup", "dinner": "pasta" }
  ],
  "checked": { "plan|veg|Томаты|шт": true },
  "manual": [
    {
      "id": "m1730553600000",
      "name": "Бумажные полотенца",
      "amount": "",
      "dept": "other",
      "source": "вручную"
    }
  ],
  "updatedAt": "2026-11-02T10:00:00.000Z"
}
```

#### Безопасность данных

- Чтение в `try/catch`, валидация структуры.
- Повреждённое значение копируется в `tarelka:state:corrupt` (без перезаписи оригинала).
- Неизвестная версия схемы → мягкий старт с чистого состояния + тост.
- При ошибке записи (приватный режим, квота) — тост, UI не ломается.
- Подробнее — `docs/spec.md`.

### Сборка списка покупок

Список не хранится — он выводится из плана + ручных позиций + отметок:

```text
для каждого рецепта в плане:
    factor = profile.people / recipe.servings
    amount = ingredient.amount × factor
```

Правила округления:

| Единица | Правило |
|---|---|
| шт, зуб., банка, ломтика | Вверх до целого, минимум 1 |
| г, мл | До 5, минимум 5 |
| ст. л., ч. л. | До 0,5 |
| Пусто / «по вкусу» | Не умножается, выводится «по вкусу» |

Дедупликация: ингредиенты с одинаковыми `name + unit + dept` суммируются. Разные единицы одного продукта остаются разными строками.

Отметки привязаны к ключу `plan|dept|name|unit`, поэтому переживают изменение порций и пересборку плана.

### Фильтры подбора

Рецепт попадает в Discover и «Собрать заново», если:

- **Категория питания:** `none` — любой рецепт; `protein` — `categories` содержит `protein`; `light` — содержит `light`; `gentle` — содержит `gentle`.
- Рецепт может входить в несколько категорий; «Без ограничений» не фильтрует каталог.
- **Аллергены:** ни один выбранный аллерген не входит в `recipe.allergens`.

Дополнительно в Discover:

- поиск по названию и ингредиентам;
- «До 20 минут» (`recipe.time ≤ 20`);
- фильтр по приёму пищи (тег «Завтрак» / «Обед» / «Ужин»).

## Серверная часть: Supabase Auth, RLS и политики

> Инфраструктура создана и проверена в Supabase, но клиент (`js/app.js`) по-прежнему читает `js/data.js` и хранит состояние в `localStorage`. Экран входа, получение сессии и чтение каталога через API — отдельная согласованная фича; её контракт зафиксирован в `docs/prd-prototype.md` §8.5, `docs/architecture.md` §11 и `docs/api-openapi.yaml` v1.1. Актуальная схема сервера — `docs/architecture.md` §8–§10.

### Auth

- В проекте включён Supabase Auth; OAuth настраивал пользователь через Supabase, секреты в репозиторий не попадали.
- Источник истины для профиля, плана, отметок и ручных позиций — Postgres. Локальный `tarelka:state` версии 1 служит офлайн-кэшем и импортируется на сервер один раз, при первом входе.
- Владение личное: каждая пользовательская строка привязана к `user_id`, общих домохозяйств нет. Отметка импорта хранится в `public.imports` и не может быть удалена клиентом.
- На момент проверки `auth.users` пуст: вход в самом приложении ещё не реализован.

### RLS

- RLS включён на всех 16 таблицах схемы `public`: 5 пользовательских (`profiles`, `week_plans`, `checked_items`, `manual_items`, `imports`) и 11 каталожных.
- Политики пользовательских таблиц сравнивают `user_id` с `(select auth.uid())` — и в `USING`, и в `WITH CHECK`. Вызов `auth.uid()` обёрнут в `select`, чтобы он вычислялся один раз на запрос.
- Функции с доступом к таблицам выполняются с `set search_path = public`.
- У ролей `anon` и `authenticated` отозвано право `TRUNCATE` на все 16 таблиц: RLS не ограничивает `TRUNCATE`, поэтому очистка таблицы обошла бы политики.
- У `authenticated` отозваны `UPDATE` и `DELETE` на `public.imports` — импорт остаётся одноразовым.

### Политики

| Таблицы | Политика | Команды | Роли | Условие |
| :-- | :-- | :-- | :-- | :-- |
| `profiles`, `week_plans`, `checked_items`, `manual_items` | `own_rows` | ALL | `authenticated` | `user_id = (select auth.uid())` для чтения, изменения и вставки |
| `imports` | `imports_select_own`, `imports_insert_own` | SELECT, INSERT | `authenticated` | только свои строки; `UPDATE`/`DELETE` не выданы |
| 11 таблиц каталога | `catalog_read` | SELECT | `anon`, `authenticated` | `using (true)` — чтение всем, записи нет |

В каталог входят `departments`, `diet_categories`, `allergens`, `tags`, `ingredients`, `recipes`, `recipe_steps`, `recipe_ingredients`, `recipe_tags`, `recipe_categories`, `recipe_allergens`.

Права на уровне таблиц:

- `anon` и `authenticated` получают `SELECT` на каталог; `INSERT`/`UPDATE`/`DELETE` на него не выданы — каталог меняют только миграции и серверные операции.
- На пользовательских таблицах `authenticated` имеет DML-гранты (`SELECT`/`INSERT`/`UPDATE`/`DELETE`), но RLS ограничивает их строками с `user_id = (select auth.uid())`; `anon` DML не имеет. `TRUNCATE` отозван у обеих ролей.
- Права `service_role` в этой настройке не изменялись; DML-гранты на пользовательские таблицы ему не выдавались.
- Остальные найденные права (`TRIGGER`, `REFERENCES`) у клиентских ролей намеренно не трогались.

Проверено через MCP: RLS включён на 16 из 16 таблиц, политик 17, security advisor без предупреждений; performance advisor показывает только 5 INFO о неиспользуемых индексах каталога.

### Миграции

Файлы лежат в `supabase/migrations/` и применены в Supabase:

| Файл | Что делает |
| :-- | :-- |
| `20261124000000_auth_rls.sql` | Пользовательские таблицы, RLS, политики `own_rows` |
| `20261124130000_auth_rls_hardening.sql` | `set search_path = public`, `(select auth.uid())`, индексы под FK |
| `20261124140000_catalog_schema.sql` | 11 таблиц каталога, RLS и `catalog_read` |
| `20261124140100_catalog_seed.sql` | Сид: 18 рецептов, 7 отделов, ингредиенты, теги, категории, аллергены |
| `20261124141000_catalog_indexes.sql` | 5 индексов под внешние ключи |
| `20261124142000_imports_policy.sql` | Только `SELECT` + `INSERT` своих строк в `imports` |
| `20261124143000_truncate_grants.sql` | Отзыв `TRUNCATE` у `anon` и `authenticated` |
| `20261124150000_validate_week_plan_fix.sql` | Исправление триггера плана: подсчёт ключей вместо несуществующей `jsonb_object_length()` |
| `20261124151000_pgtap_extension.sql` | Установка pgTAP в схему `extensions` |
| `20261124152000_api_rpc.sql` | RPC-функции плана и покупок, хелперы округления, права только для `authenticated` |
| `20261124153000_api_set_meal_null_fix.sql` | Очистка ячейки плана через `jsonb null` вместо SQL `NULL` |

### Серверный API и тесты

Пользовательские операции доступны через RPC-функции схемы `public` (вызов через Supabase REST/RPC): `api_get_plan`, `api_set_plan`, `api_set_meal`, `api_get_shopping`, `api_add_manual`, `api_remove_manual`, `api_set_checked`, `api_unset_checked`. Все они требуют вошедшего пользователя; `anon` не имеет `EXECUTE`, RLS остаётся включённой. Контракт и алгоритм сборки — в `docs/architecture.md` §10.

Тесты написаны на pgTAP и лежат в `supabase/tests/`: `api_plan_tests.sql` (16 проверок) и `api_shopping_tests.sql` (37 проверок), плюс прежний `rls_negative_tests.sql` (26 проверок). Каждый файл выполняется в транзакции с `rollback`, поэтому пробные пользователи и строки в БД не остаются. Клиентский код (`js/app.js`, `js/data.js`) в этой задаче не менялся: подключение фронта к API — отдельная согласованная фича.

### Подключение фронта (согласованный контракт)

- Вход и регистрация: email/пароль через Supabase Auth REST; подтверждение email в настройках проекта выключено, письма не отправляются, хеш пароля хранится в `auth.users`; сессия — в `tarelka:auth`, отдельно от `tarelka:state`.
- Конфигурация: `js/config.js` с адресом проекта и publishable key; секреты и `service_role` в клиент не попадают.
- Каталог читается через `GET /rest/v1/recipes`; `js/data.js` и локальные SVG остаются офлайн-резервом.
- Профиль читается и пишется прямым REST в `public.profiles` через RLS и upsert; новых RPC не добавляется.
- План и покупки идут через готовые RPC `api_*`; список покупок не собирается заново на клиенте.
- При первом входе `tarelka:state` версии 1 импортируется один раз; повторный вход серверные данные не перезаписывает.
- Без сети доступно только чтение кэша; изменения блокируются с понятным тостом.
- Ошибки Auth/REST/RPC показываются понятными сообщениями; CORS hosted Supabase проверяется в браузере на `http://localhost`.

Подробности: `docs/architecture.md` §11, `docs/spec.md` §12, `docs/ux-flows.md` §2.11, §3.4 и §4.9.

## Дизайн и UX

Визуальная концепция — тёплый пастельный wellness-food. Источник — `docs/design.md`.

Палитра (все значения — в `styles/tokens.css`):

| Токен | HEX | Назначение |
|---|---|---|
| `--color-bg` | `#FBF6EE` | Тёплый кремовый фон |
| `--color-surface` | `#FFFDF9` | Карточки |
| `--color-primary` | `#B8432E` | Томатно-паприковый акцент |
| `--color-secondary` | `#557351` | Шалфей (успех, чекбоксы) |
| `--color-text` | `#2E2622` | Тёплый тёмно-коричневый |
| `--color-text-muted` | `#6E625B` | Вторичный текст |

Типографика:

- Заголовки: Inter (если установлен) → системный стек.
- Текст: системный стек (`-apple-system`, `Segoe UI`, `Roboto`).
- Внешние шрифты не загружаются — это сохраняет офлайн и отсутствие внешних запросов.

Компоненты:

- Карточка рецепта: иллюстрация 16:9 сверху, радиус 16px, мягкая тень.
- Chip-фильтр: пилюля, `aria-pressed` для активных.
- Чекбокс: 28×28, зона клика 44×44, зачёркивание при отметке.
- Toast: снизу, `role="status"`, не забирает фокус.
- Discover: полноэкранный диалог на всех ширинах, контент колонкой до 760 px.

Чего избегаем:

- Чистый белый `#FFFFFF` как основной фон.
- Холодные цвета (синий, циан) и неон.
- Острые углы < 8px.
- Тяжёлые чёрные тени и градиенты.
- Анимации > 300ms.

## PWA и офлайн

`manifest.json`:

```text
display: standalone
theme_color: #B8432E        (совпадает с --color-primary)
background_color: #FBF6EE   (совпадает с --color-bg)
иконки: 192, 512, maskable 512
```

`sw.js`:

- `CACHE_VERSION = 'tarelka-v3'` — версия кэша в имени.
- При изменении списка файлов — поднять версию.
- Навигация: network-first с фолбэком на кэш.
- Статика: network-first с обновлением кэша.
- Не-GET и чужие origin — не трогаем.

Что работает офлайн сейчас: онбординг, план, рецепт, покупки, настройки — после первого успешного открытия. После подключения Supabase офлайн останется чтение кэша и локального каталога; изменения станут доступны только с сетью и валидной сессией.

Установка на домашний экран:

- Chrome/Edge (Android, desktop): кнопка «Установить» в адресной строке.
- Safari (iOS): «Поделиться» → «На экран "Домой"».

## Что НЕ входит в MVP

Осознанные границы (см. `docs/discussion.md` и `docs/prd.md`, раздел 3.2):

- Отдельная вкладка каталога и лента вдохновения.
- Избранное, рейтинги, комментарии, сообщество.
- Полноэкранный кулинарный режим с таймерами.
- Импорт рецептов по URL и свои рецепты.
- Шаринг и соцфункции не реализованы. Аккаунты и синхронизация пока работают только на сервере; подключение входа к клиенту согласовано как следующий этап (`docs/prd-prototype.md` §8.5).
- Несколько недель и история планов.
- Калории, БЖУ, health score, дневник питания.
- AI-подбор и рекомендации на основе поведения.
- Доставка, магазины, цены, штрихкоды.
- Подписки, реклама, партнёрские ссылки.
- Печать, копирование в буфер, экспорт/импорт JSON.
- Свайпы, долгие нажатия, drag-and-drop.
- Тёмная тема, кастомизация, мультиязычность.
- Push-уведомления, аналитика, трекинг.
