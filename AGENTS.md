# AGENTS.md — правила для AI-агента в проекте Tarelka

## 1. О продукте

**Tarelka** — веб-приложение (PWA) для планирования домашнего питания.
Пользователь собирает недельный план (завтрак / обед / ужин), смотрит рецепты
и получает автоматически собранный список покупок.

**Аудитория:** занятые люди 25–45 лет, готовят дома 3–5 раз в неделю,
хотят есть разнообразно, но не хотят тратить час на планирование.

**Jobs-to-be-done:**
- «Хочу быстро собрать план на неделю, чтобы не думать каждый вечер, что готовить»
- «Хочу один список покупок вместо десяти заметок»
- «Хочу открывать новое, но не тратить время на поиск рецептов»

**Тон голоса:** тёплый, дружелюбный, без снобизма и без инфантильности.
«Как подруга, которая хорошо готовит, но не читает лекций».
Примеры: кнопка «Запланировать», а не «Добавить в план»; пустое состояние
«Пока пусто — давай что-нибудь придумаем», а не «Нет данных».

## 2. Скоуп MVP

**Экраны прототипа:**
1. Онбординг — категория питания (Без ограничений / Много белка / Лёгкое / Щадящее), аллергии, количество человек
2. Home — недельный план 7×3 (завтрак / обед / ужин)
3. Recipe detail — ингредиенты, шаги, «добавить в список»
4. Shopping list — сгруппированный по категориям, чекбоксы
5. Discover — полноэкранный диалог с подборкой рецептов для пустой ячейки
6. «Ещё» — хаб настроек и информации
7. «Мои предпочтения» — категория питания, аллергии, порции
8. «Данные» — локальное хранение и сброс
9. «О продукте» — описание, дисклеймер, версия

**Явно вне скоупа MVP:** авторизация, бэкенд, оплата, рейтинги,
комментарии, шеринг, соцфичи, поиск, фильтры по времени/КБЖУ,
импорт рецептов по URL, несколько списков покупок, push-уведомления,
сохранённая неделя и нелюбимые продукты.

## 3. Технические ограничения

- **Стек:** чистый HTML + CSS + Vanilla JS (ES2020+). Без фреймворков,
  без npm, без сборщика. Открывается как статика.
- **Архитектура:** SPA-роутинг через `data-screen`-атрибуты, состояние
  в `localStorage`. Никаких внешних стейт-менеджеров.
- **Стилизация:** только CSS-переменные из `styles/tokens.css`.
  Хардкод цветов, шрифтов, отступов в `main.css` и `app.js` запрещён.
- **Mobile-first:** базовые стили — под мобилку (375px), расширяем через
  `min-width` media queries. Desktop — 768px и 1200px.
- **Доступность:** семантический HTML, `aria-*` там где нужно,
  focus-visible стили, контраст ≥ 4.5:1 для текста, ≥ 3:1 для UI.
  Все интерактивные элементы достижимы с клавиатуры.
- **PWA:** `manifest.json` + `sw.js` (оболочка кэшируется, сеть в приоритете). Installable; в актуальном Lighthouse отдельной категории PWA нет, поэтому установка и офлайн проверяются вручную — после первого визита приложение открывается без сети.
- **Производительность:** без тяжёлых библиотек. Изображения — локальные SVG в `assets/recipes/`, у карточек `loading="lazy"`. `<picture>` и WebP/JPEG-фолбэки не используются: SVG сам масштабируется и работает офлайн.
- **Данные:** мок-рецепты в `js/data.js`, формат — см. раздел 5.

## 5. Формат данных

**Рецепт** (в `js/data.js`):

```js
{
  id: 'tuna-rice',
  title: 'Тунец с рисом и зелёным горошком',
  time: 25,
  servings: 2,
  tags: ['Обед', 'Много белка'],
  categories: ['protein', 'light'],
  allergens: ['fish'],
  intro: '…',
  image: 'assets/recipes/tuna-rice.svg',
  ingredients: [{ name: 'Рис', amount: '100', unit: 'г' }],
  steps: ['…']
}
```

- `categories` — `protein` (много белка), `light` (лёгкое), `gentle` (щадящее).
  Рецепт может входить в несколько категорий; «Без ограничений» не фильтрует
  каталог. Пустой массив — блюдо видно только в «Без ограничений».
- `allergens` — `gluten`, `nuts`, `milk`, `eggs`, `fish`, `soy`.
- `image` — путь к локальному SVG, у каждого блюда уникальный.
- Отделы покупок (`data.departments`): `veg`, `meat`, `dairy`, `pantry`,
  `spices`, `frozen`, `other`.
- Отдел ингредиента определяется по точному названию в
  `data.ingredientCategories`; нет совпадения — `other`.

**Состояние в localStorage** — один ключ:

```
tarelka:state // версия 1
{
  "version": 1,
  "profile": {
    "onboarded": true,
    "diet": "none",
    "allergies": ["gluten"],
    "people": 4
  },
  "plan": [
    { "breakfast": "oatmeal", "lunch": "soup", "dinner": "pasta" }
  ],
  "checked": { "plan|veg|Томаты|шт": true },
  "manual": [
    {
      "id": "m1730553600000",
      "name": "Бумажные полотенца",
      "amount": "",
      "dept": "other",
      "source": "вручную"
    }
  ],
  "updatedAt": "2026-11-03T10:00:00.000Z"
}
```

- `profile.diet`: `none` | `protein` | `light` | `gentle`. Старые значения
  (`vegetarian`, `vegan`, `pescatarian`) при загрузке становятся `none`.
- `plan` — массив из 7 дней; в ячейке `breakfast` / `lunch` / `dinner`
  лежит `id` рецепта или `null`.
- Покупки отдельно не хранятся: список каждый раз собирается из `plan`.
  В `checked` — отметки по ключу `plan|<отдел>|<название>|<единица>`.
- Повреждённый JSON или неизвестная версия схемы копируются в
  `tarelka:state:corrupt`, приложение стартует с чистого состояния.
- При ошибке записи (приватный режим, квота) показывается тост, интерфейс
  продолжает работать.

## 6. Правила работы

1. **Перед каждой фичей — согласовать со мной.** Не начинать реализацию без явного подтверждения.
2. **Сначала обновляем `docs/`, потом код.** Документация описывает поведение раньше, чем оно появляется в коде.
3. **Любые редактирования — только по согласованию.** Не менять файлы, которые не входят в согласованную задачу.
4. **Ничего не удалять.** Существующие файлы, код и данные не удаляются и не перезаписываются без отдельного разрешения.
5. **Bash-команды не выполнять без спроса.** Сначала спросить, потом запускать.
6. **Работать только в папке проекта.** Не читать и не изменять файлы за пределами корня проекта.

## 7. Качество кода

- Семантический HTML: `header`, `nav`, `main`, `section`, `article`, `footer` по смыслу, а не по внешнему виду.
- Обязательные `aria`-атрибуты там, где они нужны: подписи у кнопок-иконок, `aria-label`, `aria-current`, `aria-expanded` и т.п.
- Комментарии в коде — на русском.
- Доступность не опция: управление с клавиатуры, контраст, фокус.
- Данные в `localStorage` — с версионированием и безопасной обработкой повреждённых значений.


## 8. Процесс для новой фичи

1. Согласовать задачу и границы изменений.
2. Обновить документацию в `docs/`.
3. Показать план изменений и дождаться подтверждения.
4. Реализовать: HTML → CSS (через токены) → JS.
5. Проверить мобильный вид, клавиатуру и `aria`.
6. Отчитаться, что изменено и как проверить.
