## 1. Проблема и ценность

**Проблема.** Каждый вечер пользователь решает, что готовить, а список покупок разбросан по нескольким заметкам. Поиск рецептов отнимает время, которого нет.

**Решение.** Tarelka собирает недельный план под ограничения пользователя и сразу превращает его в один список покупок. Изначально прототип работает локально, без аккаунта и сети; следующий согласованный шаг — подключение к Supabase (§8.5).

**Ценность.** План за пару минут, один список вместо десяти, новые блюда без долгого поиска.

## 2. Аудитория и Jobs-to-be-done

**Основная аудитория.** Занятые люди 25–45 лет, готовят дома 3–5 раз в неделю, хотят есть разнообразно, но не хотят тратить час на планирование.

**Функциональные задачи:**
- быстро собрать план на неделю, чтобы не думать каждый вечер, что готовить;
- получить один список покупок вместо десяти заметок;
- открывать новое, но не тратить время на поиск рецептов.

**Тон голоса.** Тёплый, дружелюбный, без снобизма и инфантильности: «как подруга, которая хорошо готовит, но не читает лекций». Кнопка «Запланировать», пустое состояние «Пока пусто — давай что-нибудь придумаем».

## 3. Принципы продукта

1. **План важнее каталога.** Главный экран — неделя, а не лента рецептов.
2. **Готовый результат с первого запуска.** Онбординг заканчивается планом, а не пустым экраном.
3. **Один тап до действия.** Все действия видны; свайпов, долгих нажатий и drag-and-drop нет.
4. **План и список — одно целое.** Изменение плана сразу отражается в покупках.
5. **Приватность по умолчанию.** Аналитики нет; пользовательские данные привязаны к личному аккаунту и защищены RLS (§8.5). Без сети доступен только кэш для чтения.

## 5. Ключевые сценарии

1. **Первый запуск.** Пройти 3 шага онбординга → получить план на неделю.
2. **Планирование.** Открыть пустую ячейку → выбрать рецепт в Discover → ячейка заполнена.
3. **Готовка.** Открыть карточку рецепта → посмотреть шаги → добавить ингредиенты в покупки.
4. **Магазин.** Открыть «Покупки» → отметить купленное → вернуться к списку.
5. **Изменения.** Убрать блюдо из плана → список покупок пересчитан, ручные позиции и отметки остаются.
6. **Настройки.** Изменить предпочтения или сбросить данные в «Ещё».

## 6. Функциональные требования

| ID | Требование |
| :-- | :-- |
| FR-01 | Онбординг из 3 шагов: категория питания (`none`, `protein`, `light`, `gentle`), аллергии (фиксированный список из 6), количество человек (2/4/6). Любой шаг можно пропустить; после онбординга те же поля доступны в «Мои предпочтения». |
| FR-02 | План — 7 дней по 3 слота (`breakfast`, `lunch`, `dinner`). В ячейке лежит `id` рецепта или `null`. Сегодняшний день выделен. |
| FR-03 | Discover открывается из пустой ячейки как полноэкранный диалог. Тап по карточке открывает рецепт, кнопка «+» назначает его в целевую ячейку. |
| FR-04 | Подборка фильтруется по категории питания и аллергенам. «Без ограничений» не фильтрует каталог; рецепт может входить в несколько категорий. |
| FR-05 | Карточка рецепта показывает иллюстрацию, ингредиенты, шаги и позволяет добавить ингредиенты в список покупок. Пересчёт идёт под количество человек. |
| FR-06 | Список покупок выводится из плана: ингредиенты суммируются, группируются по отделам, имеют чекбоксы и прогресс. |
| FR-07 | Ручные позиции добавляются в список и не исчезают при изменении плана. Отметки хранятся по ключу `plan|отдел|название|единица`. |
| FR-08 | В «Ещё» доступны изменение предпочтений, объяснение локального хранения, сброс данных по подтверждению и блок «О продукте» с дисклеймером. |
| FR-09 | Состояние хранится в одном ключе `tarelka:state` версии 1. Повреждённые данные копируются в `tarelka:state:corrupt`, приложение стартует с чистого состояния. Ошибка записи показывается тостом и не ломает интерфейс. |
| FR-10 | Каталог — 18 собственных рецептов с уникальными локальными SVG-иллюстрациями. |
| FR-11 | Вход и регистрация через Supabase Auth без подтверждения по почте. Пользовательские данные доступны только после входа. |
| FR-12 | Сервер — источник истины: профиль, план, отметки и ручные позиции хранятся в Postgres; `localStorage` служит офлайн-кэшем. |
| FR-13 | Доступ к строкам ограничен политиками RLS по `user_id = auth.uid()`; пользователь видит и меняет только свои данные. |
| FR-14 | При первом входе локальное состояние версии 1 импортируется на сервер один раз; при повторном входе импорт не повторяется. |
| FR-15 | Каталог рецептов хранится в Postgres в нормализованном виде: рецепты, шаги, ингредиенты, отделы, теги, категории и аллергены. |
| FR-16 | Все данные из `js/data.js` перенесены сидом: 18 рецептов, 7 отделов, соответствия ингредиентов отделам. Демо-неделя не переносится. |
| FR-17 | Каталог доступен на чтение `anon` и `authenticated`; изменение каталога доступно только `service_role` и миграциям. |
| FR-18 | `js/data.js` и локальные SVG не удаляются: файл остаётся офлайн-резервом, изображения хранятся в `assets/recipes/`. |
| FR-19 | Серверный API предоставляется RPC-функциями в схеме `public` и вызывается через Supabase REST/RPC. Все пользовательские операции требуют вошедшего пользователя и работают только с его `user_id`; `anon` не имеет доступа к вызовам. |
| FR-20 | CRUD плана: чтение недели 7×3, полная замена, назначение и очистка ячейки. Неизвестные `id` рецептов при записи превращаются в `null`, как при загрузке локального состояния. |
| FR-21 | CRUD покупок: получение собранного списка, добавление и удаление ручных позиций, установка и снятие отметок по ключам `plan\|отдел\|название\|единица` и `manual\|id`. |
| FR-22 | Сборка списка покупок на сервере повторяет `docs/spec.md` §5.1–§5.3: множитель `people / servings`, округление по единицам, суммирование до округления, дедупликация по названию + единице + отделу, группировка по отделам, `done` из отметок. |
| FR-23 | Вход и регистрация по email и паролю выполняются через Supabase Auth REST без внешних библиотек. В проекте Supabase отключено подтверждение email: регистрация сразу возвращает сессию, письма не отправляются, хеш пароля хранится в `auth.users`. Сессия (access token, refresh token, срок действия) хранится в отдельном ключе `tarelka:auth`, а не внутри `tarelka:state`. |
| FR-24 | Адрес проекта Supabase и publishable key лежат в `js/config.js`. Секреты, service_role и приватные ключи в клиентский код не попадают. |
| FR-25 | Каталог рецептов читается из Postgres через Supabase REST. `js/data.js` и локальные SVG остаются офлайн-резервом; неизвестный `id` рецепта в плане не ломает интерфейс. |
| FR-26 | Профиль читается и пишется прямым REST-запросом в `public.profiles` через RLS (`user_id = auth.uid()`) с upsert; новые RPC для профиля не создаются. |
| FR-27 | План и покупки читаются и изменяются готовыми RPC `api_*`: чтение/замена плана, назначение и очистка ячейки, сборка покупок, ручные позиции и отметки. |
| FR-28 | При первом успешном входе локальное состояние версии 1 один раз импортируется на сервер. После этого сервер — источник истины, а `tarelka:state` используется как кэш и не перезаписывает серверные данные при повторном входе. |
| FR-29 | Без сети или без успешной авторизации приложение показывает кэш только для чтения. Все мутирующие действия заблокированы и объясняются тостом; повторить их можно после восстановления сети и входа. |
| FR-30 | Ошибки сети, авторизации и API показываются понятными тостами без технических деталей; повторные запросы не создают дубли. CORS для hosted Supabase REST/RPC проверяется в браузере на `http://localhost`. |

## 8. Что не входит и открытые вопросы

**Вне скоупа прототипа:** авторизация, бэкенд, оплата, рейтинги, комментарии, шеринг, соцфичи, поиск, фильтры по времени и КБЖУ, импорт рецептов по URL, несколько списков покупок, push-уведомления, сохранённая неделя и нелюбимые продукты.

> Исключение после решения №1 (§8.1): поиск и фильтр «до 20 минут» в Discover остаются в прототипе. Фильтры по КБЖУ по-прежнему вне скоупа.

## 9. Критерии готовности

- Все 9 экранов доступны и работают офлайн после первого открытия.
- В каталоге 18 рецептов с локальными SVG-иллюстрациями, ингредиентами и шагами.
- План, покупки и настройки переживают перезагрузку страницы.
- Повреждённый JSON не ломает приложение; сброс данных требует подтверждения.
- Интерфейс проверен на 360 px, с клавиатуры и со скринридером; нет горизонтальной прокрутки.
- Приложение устанавливается на домашний экран и запускается в standalone-режиме.
- В прототипе нет функций из раздела 8, кроме явно отмеченных открытых вопросов.

> Уточнение после закрытия расхождений: решение №1 в §8.1 означает, что поиск и фильтр «до 20 минут» в Discover остаются в прототипе; остальные пункты раздела 8 остаются вне скоупа.

Критерии авторизации:

- Вход и регистрация работают, регистрация не отправляет письма; RLS изолирует данные разных пользователей.
- При первом входе локальные данные переносятся на сервер один раз.
- Повторный вход не создаёт дублей и не перезаписывает серверные данные локальными.

Критерии каталога:

- В БД загружены все 18 рецептов, их шаги и ингредиенты, 7 отделов и все соответствия ингредиентов отделам.
- Каталог читается анонимно и авторизованными пользователями; клиентские роли не могут его изменить.
- `js/data.js` и SVG-иллюстрации сохранены; клиентский код в этой задаче не менялся.

Критерии API:

- Все RPC-вызываемые функции доступны только вошедшему пользователю и работают только со своими строками.
- Чтение, замена и точечное изменение плана проходят валидацию 7 дней × 3 слота; неизвестные рецепты превращаются в `null`.
- Список покупок собирается по правилам округления и дедупликации из `docs/spec.md` §5.1–§5.3; отметки не зависят от количества и сохраняются при пересборке.
- Тесты pgTAP в `supabase/tests/` проходят от красного этапа к зелёному; после прогона в БД не остаётся пробных данных.
- Триггер `validate_week_plan()` больше не вызывает несуществующую функцию и разрешает корректную запись плана.

Критерии подключения фронта:

- Экран входа/регистрации получает сессию по email/паролю; при регистрации письма не отправляются, сессия выдаётся сразу; без сессии пользовательские данные не доступны.
- Каталог, профиль, план и покупки загружаются из Supabase; `js/data.js` используется только как офлайн-резерв.
- Профиль сохраняется прямым REST в `public.profiles`, план и покупки — через готовые RPC.
- Локальное состояние версии 1 импортируется один раз при первом входе и больше не перезаписывает сервер.
- Без сети доступно только чтение кэша; попытки изменения показывают понятный тост.
- Ошибки сети/авторизации/API не ломают интерфейс; CORS проверен в браузере с `http://localhost`.
- В клиентском коде нет секретов и `service_role`; конфигурация вынесена в `js/config.js`.
