## 2. Краткое резюме

1. Tarelka — планировщик питания: недельный план, рецепты и список покупок; без бэкенда, аккаунтов и аналитики.
2. Стек MVP — только HTML, CSS и JavaScript, mobile-first PWA; все данные в одном версионированном ключе `tarelka:state`.
3. Главный сценарий: онбординг из 4 шагов → автоплан на текущую неделю → добавление или замена блюд → рецепт → список покупок.
4. Онбординг: тип питания, аллергии, нелюбимые продукты, порции 2/4/6; каждый шаг можно пропустить.
5. Ограничения: тип питания и аллергии — жёсткие фильтры; нелюбимые продукты исключаются только из автоподбора.
6. Контент: 40–60 своих рецептов в локальном JSON и локальные WebP-фото с реестром источников.
7. Данные: одна активная неделя и один шаблон; ручные позиции и отметки покупок сохраняются при изменениях плана.
8. UX: три вкладки «План», «Покупки», «Ещё»; только тапы; оптимистичные обновления с откатом и undo на 5 секунд.
9. Доступность и производительность: WCAG 2.1 AA, зоны 44×44, клавиатура, 360 px; автоподбор ≤ 2 с, первая загрузка ≤ 1,5 МБ.
10. Границы: нет каталога, избранного, кулинарного режима, аккаунтов, синхронизации, печати, экспорта, тёмной темы и AI.

## 3. Что зафиксировано

| Решение | Детали |
| :-- | :-- |
| **Главный экран** | Неделя пн–вс, сегодняшний день выделен и прокручен в видимую область. |
| **День** | Список блюд и необязательная заметка. Жёстких слотов «завтрак/обед/ужин» нет. |
| **Навигация** | Три вкладки: «План», «Покупки», «Ещё». Выбор рецепта — не вкладка, а экран из дня. |
| **Порции** | 2/4/6. Штучные округляются вверх, граммы и миллилитры не переводятся, «по вкусу» не умножается. |
| **Повторы** | Разрешены. Порции складываются, одинаковые ингредиенты в одной единице суммируются. |
| **Покупки** | Список производный от плана, обновляется автоматически. Ручные позиции и отметки сохраняются. |
| **Шаблон** | Один безымянный шаблон «Сохранённая неделя»: блюда, порции, заметки. |
| **Хранение** | Один ключ, версия схемы, миграция, резервная копия повреждённых данных, сброс только с подтверждением. |
| **Диалоги** | Mobile — полноэкранный диалог, desktop — модальное окно. Bottom sheet в MVP не используется (PRD A5). |
| **Обратимость** | Удаление, перемещение, замена и смена порций — с undo на 5 секунд. Сброс и шаблон — с подтверждением. |
| **Доступность** | Семантический HTML, aria, фокус, клавиатура, контраст AA, зоны 44×44, `prefers-reduced-motion`. |
| **Приватность** | Нет внешних запросов, шрифтов с CDN, аналитики и трекинга. |

## 6. Открытые вопросы

| № | Вопрос | Почему важно | Когда закрыть |
| :-- | :-- | :-- | :-- |
| 1 | Кто пишет 40–60 рецептов и откуда берутся фото с допустимыми лицензиями? | Без контента нет продукта; фото — юридический риск. | До производства контента и вёрстки карточек. |
| 2 | Финальная формулировка дисклеймера по аллергенам. | Тон и юридическая безопасность. | До текстов онбординга, рецепта и «О продукте». |
| 3 | Финальный список аллергенов и типов питания. | Влияет на разметку рецептов и фильтры. | До заполнения JSON рецептов. |
| 4 | Нужен ли мягкий индикатор «Вы офлайн». | Не блокирует работу, но влияет на состояния. | До UI-полировки. |
| 5 | Нужно ли массовое снятие отметок в покупках. | Сейчас снимаем вручную; кандидат после пилота. | После пилота, не блокирует MVP. |

## 7. С чего начать разработчику

1. Прочитать `AGENTS.md`, `docs/prd.md`, `docs/design.md`, `docs/ux-flows.md`.
2. Проверить, что дизайн и UX согласованы; зафиксировать замечания в документах, а не только в чате.
3. Закрыть вопросы по контенту, лицензиям, аллергенам и дисклеймеру.
4. Написать `docs/spec.md`: экранные сценарии, состояния, структура данных, миграции.
5. Согласовать план реализации и порядок файлов.
6. Только после этого писать код: HTML → CSS через `styles/tokens.css` → JS.
7. Перед каждым PR проверять мобильный вид, клавиатуру, `aria`, контраст и офлайн.

**Нельзя без отдельного согласования:**

- добавлять функции из out-of-scope;
- менять модель хранения, недели или шаблона;
- вводить фреймворки, библиотеки, сборщики или внешние запросы;
- заменять полноэкранные диалоги bottom sheet;
- менять палитру вне токенов;
- удалять существующие данные, файлы или решения.

## 8. Критерии приёмки Handoff-пакета

- [ ] Разработчик может пересказать главный сценарий и границы MVP без подсказок.
- [ ] Понятно, где лежат правила, требования, визуальные токены и UX-флоу.
- [ ] Понятно, что код ещё не начат и следующий шаг — SPEC, а не сразу вёрстка.
- [ ] Понятно, какие документы уже утверждены, а какие ждут согласования.
- [ ] Понятно, что контент и лицензии на фото — критический путь.
- [ ] Зафиксировано, какие действия обратимы через undo, а какие требуют подтверждения.
